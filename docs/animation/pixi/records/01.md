# 一、pixi使用中遇到的问题

## 1.1 pixi.js的画布超过 16384px 开始抽风

**PixiJS 宽度超过 16384px 就异常，根本原因是 GPU 纹理尺寸硬限制（WebGL 上限），不是 Pixi 本身 bug。**
**用多个 Pixi 实例横向拼接（多画布）完全合理、是工业级长场景标准方案。**

### 1. 为什么 16384 是一道坎
- **GPU 纹理上限**：绝大多数桌面显卡 WebGL 最大纹理尺寸 **16384×16384**（部分高端 32768）。
- **面积限制**：Chrome 等浏览器 Canvas 总面积上限约 **268,435,456 像素 = 16384×16384**。
- **表现**：超过后渲染错乱、黑屏、闪烁、元素消失、性能暴跌。

### 2. 单 PIXI 实例的缓解方案

改用 **视口 + 内容平移**（不放大画布）

```javascript
// 画布保持屏幕宽（如 1920），内容放在超大 Container 里
const app = new PIXI.Application({ width:1920, height:1080 });
const world = new PIXI.Container();
app.stage.addChild(world);

// 内容全部加到 world，宽度设 50000
const bg = new PIXI.Graphics().rect(0,0,50000,1080).fill(0x333);
world.addChild(bg);

// 滚动时平移 world，而非改画布宽
function scrollTo(x){ world.x = -x; }
```
**优点**：完全避开尺寸限制、性能最好。
**缺点**：鼠标/触摸坐标要做 **世界坐标 ↔ 屏幕坐标** 转换。


### 3. 多 PIXI 实例横向拼接（最推荐：无限宽、稳定、高性能）

**完全合理，是长场景、无限画布、超大地图的标准方案。**

1. 核心思路
	- 多个 `<canvas>` 横向**无缝并排**（CSS: `display:inline-block; white-space:nowrap`）。
	- 每个 Pixi 宽 **≤16384**（建议 8192/10240，更稳）。
	- 共享**同一逻辑世界坐标**，滚动时同步平移所有实例。
	- 鼠标/事件统一转发、坐标归一化。

2. 简易实现（伪代码）

	```html
	<!-- DOM -->
	<div id="pixi-container" style="overflow:hidden; width:100vw; height:1080px; white-space:nowrap;"></div>
	```

	```javascript
	const SECTION_W = 8192;   // 每段宽
	const TOTAL_W = 50000;    // 总宽
	const sections = [];
	const container = document.getElementById('pixi-container');

	// 创建多实例
	for(let x=0; x<TOTAL_W; x+=SECTION_W){
	  const app = new PIXI.Application({
	    width: Math.min(SECTION_W, TOTAL_W-x),
	    height:1080,
	    backgroundColor:0x222
	  });
	  app.view.style.display = 'inline-block';
	  container.appendChild(app.view);
	  sections.push({ app, offsetX:x });
	}

	// 全局滚动控制
	let scrollX = 0;
	function setScroll(x){
	  scrollX = x;
	  sections.forEach(({app, offsetX})=>{
	    app.stage.x = offsetX - x; // 关键：错位偏移
	  });
	}

	// 示例：滚动到 20000
	setScroll(20000);
	```

## 1.2 PixiJS实现 阻止冒泡

在 PixiJS 中，**阻止事件冒泡**用：

```js
e.stopPropagation();
```

但必须满足两个前提：

- 事件必须是 **Pixi 原生事件**（pointerdown /pointermove 等）
- 元素必须开启交互：`eventMode = 'static'` 或 `'dynamic'`


## 1.3 延时触发拖拽

在 PixiJS 可视化、画布拖拽交互开发中，我们经常遇到需求：**鼠标按住一段时间（例如300ms）后，才正式激活拖拽逻辑**。
绝大多数开发者第一选择是使用 `setTimeout` 实现延时。但在 Pixi 高负载画布场景（大量精灵渲染、纹理更新、`VideoFrame` / `ImageBitmap` 贴图实时刷新）下，原生定时器存在大量难以复现的计时漂移、延迟甚至“假卡死”问题。
结合 PixiJS 渲染线程特性与浏览器事件机制，**`mouseDownStamp + mousemove 时间戳判断`** 是更稳定的工程方案。


### 1.3.1 传统 setTimeout（含 Web Worker 定时器）底层缺陷

1. 主线程阻塞导致定时器不准

    浏览器 `setTimeout` 基于**宏任务队列**。

    当 PixiJS 主线程持续执行渲染、纹理上传、碰撞检测、大量图形绘制等同步任务时，事件队列排队阻塞。即便设置延迟300ms，实际触发时间可能延迟500ms~1000ms。

2. Web Worker 方案依旧存在短板

    很多人会引入 Web Worker 分离定时器：

    -  Worker 内部 `setTimeout` 计时不受主线程运算阻塞；
    - **致命局限**：Worker 计时完成后，依靠 `postMessage` 发送通知。消息抵达主线程依旧进入主线程事件队列排队。

    如果此时 Pixi 渲染循环满载，回调依旧延迟执行。

    同时标签页切后台、最小化时，浏览器会对 Worker 定时器进行节流，依然会出现计时漂移。

3. 频繁鼠标交互引发时序混乱

    拖拽交互高频触发 `mousedown`，连续创建/清除定时器容易出现：旧定时器延迟触发、多次回调冲突，必须额外维护全局状态、任务ID、清理函数，代码复杂度显著上升。

### 1.3.2 `mouseDownStamp` 时间戳方案原理

- 核心思路

    1. `mousedown` 按下瞬间，记录当前高精度时间戳 `mouseDownStamp = performance.now()`；
    2. 在持续触发的 `mousemove` 事件中，实时计算当前时间与按下时间差值；
    3. 差值 ≥ 设定延时阈值时，激活拖拽标记 `isDragging = true`；
    4. `mouseup` 鼠标抬起，直接清空时间戳，终止本次按压流程。

-  最简参考代码

    ```js
    let mouseDownStamp = 0;
    let isDragging = false;
    const DRAG_DELAY = 300; // 按住300ms后启动拖拽

    // 鼠标按下
    function onMouseDown() {
        mouseDownStamp = performance.now();
        isDragging = false;
    }

    // 鼠标移动
    function onMouseMove() {
        // 鼠标未按下 / 拖拽已经激活，直接返回
        if (mouseDownStamp === 0 || isDragging) return;

        const now = performance.now();
        if (now - mouseDownStamp >= DRAG_DELAY) {
            isDragging = true;
            console.log("拖拽正式激活");
        }
    }

    // 鼠标抬起
    function onMouseUp() {
        mouseDownStamp = 0;
        if (isDragging) {
            console.log("拖拽结束");
        }
        isDragging = false;
    }
    ```

    > 限制说明：
    > 鼠标按住**完全不移动**时，不会触发 `mousemove`，延时逻辑无法执行。
    > 如果业务强制要求「按住鼠标原地不动也能触发拖拽」，此方案无法满足，仍然需要定时器方案。

### 1.3.3 时间戳方案相比定时器的核心优势

1. 不受主线程阻塞影响，计时逻辑稳定可靠

    `performance.now()` 获取高精度单调递增时间。判断逻辑仅做一次减法运算，**不存在任务排队问题**。
    不管 PixiJS 主线程渲染压力多大、大量 `VideoFrame`/纹理上传占用资源，时间差值计算永远准确，不会出现计时严重漂移。

2. 无浏览器后台节流风险

    `setTimeout`（包括 Worker）在页面切后台、窗口最小化时，浏览器会限制定时器最低调度间隔（通常1000ms）。
    时间戳方案依靠鼠标原生输入事件，不存在浏览器策略层面的节流限制。

3. 代码简洁，无需维护定时器生命周期

    - 不需要创建 Worker、不需要 Blob 内联脚本；
    - 无需手动 `clearTimeout`、不需要管理任务ID、消息通信；
    - 无需关心 Worker 销毁、内存泄漏、CSP策略兼容问题；
    - 状态变量极少，仅 `mouseDownStamp`、`isDragging`，易于调试。

4. 天然适配拖拽交互模型

    拖拽本身依赖 `mousemove` 事件持续驱动。

    我们复用已有事件循环，**不新增任何事件与任务**，不会额外增加主线程负担，完美契合 PixiJS 画布交互架构。

5. 状态逻辑清晰，不存在误触发问题
    定时器经典BUG：鼠标快速按下抬起，定时器依旧延迟执行，导致拖拽意外激活。
    
    时间戳方案：`mouseup` 直接清空 `mouseDownStamp`。只要鼠标抬起，后续所有判断直接失效，从根源杜绝延时回调误执行。

6. 调试成本极低

    任意位置打印时间戳差值，直观查看按压时长；没有跨线程消息、异步时序问题，断点调试不需要跟踪多线程通信。
