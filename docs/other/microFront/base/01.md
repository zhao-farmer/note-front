
# 一、微前端原理

微前端（Micro Frontends）是一种**将前端应用拆分为多个小型、独立、可独立开发、测试、部署和运行的前端模块**的架构模式。它的核心思想借鉴自后端的**微服务架构**，目标是解决大型前端单体应用（Monolithic Frontend）带来的协作、维护和扩展难题。


## 1.1 核心概念

1. **独立性**

    *   每个微前端应用（也叫“子应用”或“微应用”）由不同的团队独立开发、构建、测试和部署。
    *   技术栈可以不同（如 React、Vue、Angular、Svelte 等共存）。

2. **组合性**

    *   多个微前端在运行时被**集成到同一个页面**中，对用户来说是一个完整的产品。
    *   通常有一个**主应用（Container/Shell）** 负责协调路由、加载子应用、共享状态等。

3. **自治性**

    *   子应用之间尽量**低耦合**，通过定义良好的接口（如 props、事件、全局状态）通信。
    *   一个子应用的故障不应导致整个系统崩溃。


## 1.2 微前端 vs 单体前端

| 维度  | 单体前端 | 微前端 |
| --- | --- | --- |
| 团队协作 | 所有团队共用一个代码库，易冲突 | 各团队独立开发子应用 |
| 技术栈 | 统一（如全用 React） | 可混用（React + Vue + Angular） |
| 构建部署 | 整体构建、整体上线 | 独立构建、独立部署 |
| 扩展性 | 随着项目变大，构建慢、维护难 | 按需扩展，只改相关子应用 |
| 初期成本 | 低   | 较高（需搭建基础设施） |



## 1.3 微前端的实现原理

微前端的关键在于**如何在运行时动态加载并集成多个独立的前端应用**。常见实现方式包括：

1. **iframe 嵌入（简单但局限）**

    *   每个子应用用 `<iframe>` 加载。
    *   隔离性好（CSS/JS 不冲突）
    *   SEO 差、通信复杂、URL 同步难、性能开销大
    *   一般不推荐用于主流微前端方案。

2. **JS 动态加载 + DOM 操作（主流方式）**

    *   主应用通过 `import()` 或 `<script>` 动态加载子应用的 JS bundle。
    *   子应用暴露生命周期钩子（如 `bootstrap`, `mount`, `unmount`）。
    *   主应用调用这些钩子，将子应用的 DOM 插入指定容器。

    > **典型框架**：
    > 
    > *   Single-SPA（最流行的微前端框架）
    > *   qiankun（蚂蚁金服开源，基于 single-spa，增强沙箱隔离）

    #示例流程（以 qiankun 为例）：

    1.  用户访问主应用（如 `https://main.com`）
    2.  主应用根据路由判断需要加载哪个子应用（如 `/app1` → 加载 `app1`）
    3.  主应用动态加载 `app1` 的 JS 文件
    4.  调用 `app1.mount()`，将 `app1` 的 UI 渲染到 `<div id="container"></div>`
    5.  用户操作 `app1`，其内部逻辑独立运行

3. **Web Components（标准化方案）**

    *   子应用封装为自定义元素（Custom Elements）。
    *   主应用像使用普通 HTML 标签一样使用 `<my-app1></my-app1>`。
    *   标准化、天然隔离
    *   浏览器兼容性、生态工具支持有限

4. **Module Federation（Webpack 5 原生支持）**

    *   利用 Webpack 5 的 **Module Federation** 特性，直接在构建时共享模块。
    *   子应用可作为“远程模块”被主应用按需加载。
    *   构建时集成，性能好
    *   要求所有子应用使用 Webpack 5，技术栈受限

## 1.4 关键技术挑战与解决方案

    | 挑战  | 解决方案 |
    | --- | --- |
    | **样式隔离** | CSS-in-JS、命名空间、Shadow DOM、qiankun 的沙箱机制 |
    | **JS 全局污染** | 沙箱（如 proxy 代理 window）、严格模式、避免全局变量 |
    | **公共依赖重复加载** | 主应用提供共享依赖（如 React、Lodash），子应用 external 掉 |
    | **跨应用通信** | 自定义事件（`dispatchEvent`）、全局状态管理（Redux/Zustand）、props 传递 |
    | **路由同步** | 主应用统一管理路由，子应用使用内存路由或监听 URL 变化 |
    | **本地开发调试** | 支持独立启动子应用 + mock 主容器环境 |
