一、认识 WebCodecs

  • webcodecs MDN文档
  • webcodecs 谷歌使用

1.1 WebCodecs 是什么？解决了什么问题？

WebCodecs API 是浏览器提供的原生音视频编解码底层接口，为 Web 开发者提供了对视频流单个帧和音频数据块的直接访问能力。

  1. 传统方案的痛点
    • 现有 Web 媒体 API（WebRTC、MediaRecorder、MediaSource）只能处理高级别的媒体流，无法访问单个帧和原始编码数据
    • 开发者被迫使用 WebAssembly 打包编解码器（如 FFmpeg.wasm），导致：
      • 额外下载数百 KB 甚至 MB 的编解码器代码
      • 无法利用浏览器内置的硬件加速能力，CPU 占用高、性能差
      • 开发和维护成本高
  2. WebCodecs 的核心价值
    • 直接复用浏览器内置的硬件加速编解码器（H.264、VP8、VP9、AV1 等）
    • 提供对原始视频帧（VideoFrame）、音频数据（AudioData）和编码块的完全控制
    • 异步执行所有繁重工作，不阻塞主线程
    • 与其他 Web API（Canvas、WebGL、MediaStream）无缝集成
  3. 适用场景
    • 视频/音频编辑器（逐帧处理、特效添加）
    • 低延迟视频会议（实时编码/解码）
    • 自定义流媒体协议（如 WebTransport 传输编码块）
    • 动画图像解码（GIF、APNG、WebP 动画）
    • 云游戏、实时屏幕共享

1.2 核心接口总览

WebCodecs API 包含以下 12 个核心接口，覆盖音视频编码、解码和图像处理全流程：

类别接口功能描述
视频处理VideoEncoder将 VideoFrame 编码为 EncodedVideoChunk
VideoFrame表示一帧未编码的原始视频数据
EncodedVideoChunk表示编码后的视频字节块
VideoDecoder将 EncodedVideoChunk 解码为 VideoFrame
VideoColorSpace表示视频帧的颜色空间信息
音频处理AudioEncoder将 AudioData 编码为 EncodedAudioChunk
AudioData表示未编码的原始音频数据
EncodedAudioChunk表示编码后的音频字节块
AudioDecoder将 EncodedAudioChunk 解码为 AudioData
图像处理ImageDecoder解包和解码图像数据，支持动画图像
ImageTrackList表示图像中可用的轨道列表
ImageTrack表示单个图像轨道

1.3 核心使用流程

整体原则：配置校验 → 实例化编解码器绑定回调 → 送入原始/编码数据 → 回调产出结果 → 使用完成必须 close() 释放资源

1.3.1 视频编码

流程链路 原始视频源（Canvas / MediaStream / OffscreenCanvas） → 生成 VideoFrame → VideoEncoder.encode() → 回调输出 EncodedVideoChunk → MP4Box/Mediabunny 封装成 MP4 / WebTransport 发送网络 → 使用完毕 frame.close()

步骤拆解：

  1. 使用 VideoEncoder.isConfigSupported() 校验编码配置是否被浏览器支持
  2. 实例化 VideoEncoder，传入 output（接收编码后块）、error（错误回调）
  3. 调用 encoder.configure(config) 设置分辨率、帧率、码率、codec（如 avc1.42E01E H.264）
  4. 循环生成 VideoFrame（从 canvas 或 MediaStreamTrackProcessor 获取）
  5. 调用 encoder.encode(videoFrame, options)，可标记是否为关键帧 keyFrame:true
  6. output 回调拿到 EncodedVideoChunk，做封装或者网络传输
  7. 每帧处理完必须执行 videoFrame.close()，防止内存暴涨
  8. 全部结束调用 encoder.flush() 刷完队列剩余数据，再 encoder.close()

      生成 VideoFrame
           ↓
 VideoEncoder.encode()
           ↓
      output 回调
           ↓
   EncodedVideoChunk
           ↓
封装MP4 / 网络发送
           ↓
    VideoFrame.close()
           ↓
继续下一帧 / flush + close

1.3.2 视频解码

流程链路 码流来源（网络接收 / MP4 解封装） → EncodedVideoChunk → VideoDecoder.decode() → output 回调输出 VideoFrame → Canvas/GL 渲染画面 → frame.close()

步骤拆解：

  1. VideoDecoder.isConfigSupported() 校验解码配置
  2. 实例化 VideoDecoder，绑定 output、error 回调
  3. decoder.configure(config) 设置 codec 等参数
  4. 解封装得到 EncodedVideoChunk（区分 key / delta 帧）
  5. 调用 decoder.decode(chunk) 送入解码器
  6. output 回调得到 VideoFrame，绘制到 canvas / 上传 WebGL 纹理
  7. 渲染完成后立即 frame.close()
  8. 结束执行 decoder.flush()、decoder.close()

   VideoFrame.close()
          ↓

1.3.3 音频编码

流程链路 音频源（MediaStream、AudioContext） → 生成 AudioData → AudioEncoder.encode() → output 回调输出 EncodedAudioChunk → 封装进媒体文件 / 网络传输 → audioData.close()

步骤拆解：

  1. AudioEncoder.isConfigSupported() 校验音频配置（采样率、声道数、codec:aac）
  2. 创建 AudioEncoder，设置 output、error 回调
  3. encoder.configure() 设置采样率、声道、比特率
  4. 构造 AudioData 对象，传入 PCM 原始音频样本
  5. 调用 audioEncoder.encode(audioData)
  6. output 获取 EncodedAudioChunk，参与封装或网络发送
  7. audioData.close() 释放音频内存
  8. 完成后 flush() → close()

1.3.4 音频解码

流程链路 音频码流 → EncodedAudioChunk → AudioDecoder.decode() → output 产出 AudioData → AudioContext 播放音频 → audioData.close()

步骤拆解：

  1. AudioDecoder.isConfigSupported() 校验解码配置
  2. 实例化 AudioDecoder，绑定 output、error
  3. decoder.configure()
  4. 送入 EncodedAudioChunk，调用 decoder.decode(chunk)
  5. output 拿到 AudioData，可喂给 AudioContext 输出声音
  6. 使用完执行 audioData.close()
  7. 结束 flush()、close()

1.3.5 图片处理 ImageDecoder

专门处理静态图、动图 GIF / APNG / WebP，不需要视频解码器，直接解析二进制图片数据输出帧。

流程链路 图片二进制 ArrayBuffer → ImageDecoder 创建实例 → 调用 decode() → 获取 ImageDecodeResult，里面包含 VideoFrame → 绘制画面 → frame.close()

步骤拆解：

  1. 传入图片二进制数据创建 ImageDecoder({data: buffer, type:'image/gif'})
  2. 获取 tracks，选择需要解码的图像轨道
  3. 调用 decoder.decode({frameIndex: n}) 异步解码某一帧
  4. 返回结果 result.image 得到 VideoFrame，绘制到 canvas
  5. 使用结束 frame.close()；全部完成调用 decoder.close()

1.4 最佳实践与注意事项

  1. 内存管理（至关重要！）
    • 必须在 VideoFrame、AudioData、EncodedVideoChunk 使用完毕后调用 close() 方法释放底层内存
    • 不调用 close() 会导致严重的内存泄漏，浏览器会在垃圾回收时才释放，但会造成内存占用飙升
  2. 使用 Web Worker 处理帧
    • 帧和编码块回调每秒会调用数十次，容易阻塞主线程
    • 建议将所有编解码逻辑移到 Web Worker 中执行
    • VideoFrame 和 EncodedVideoChunk 都是可传输对象（Transferable），可以在主线程和 Worker 之间高效传递
  3. 队列控制
    • 监控 encoder.encodeQueueSize 和 decoder.decodeQueueSize
    • 当队列过大时，适当丢弃非关键帧（delta 帧）
    • 避免队列积压导致内存溢出和延迟增加
  4. 编解码器选择
    • 优先使用硬件加速的编解码器（H.264、VP9、AV1）
    • 使用 VideoEncoder.isConfigSupported() 和 VideoDecoder.isConfigSupported() 提前检测支持情况
    • 准备降级方案（如 WebAssembly）以应对不支持的浏览器
  5. 调试工具
    • 使用 Chrome DevTools 的媒体面板（Media Panel）查看 WebCodecs 日志和状态
    • 可以查看编码器/解码器的配置、队列大小、错误信息等详细数据

1.5 与其他 API 的配合

  • MediaStreamTrackProcessor/Generator：将 MediaStream 转换为帧流，或将帧流转换回 MediaStream
  • Insertable Streams API：与 WebRTC 集成，实现自定义媒体处理管道
  • Canvas API：直接在 Canvas 上绘制 VideoFrame，或从 Canvas 创建 VideoFrame
  • WebGL/WebGPU：将 VideoFrame 作为纹理上传到 GPU，实现硬件加速的视频特效
  • OffscreenCanvas：在 Web Worker 中直接渲染帧，完全脱离主线程
