二、浏览器的安全策略限制

2.1 安全策略列表

自动播放策略

  1. 有声媒体禁止自动播放 带有声音的 <video> 或 <audio> 元素不允许自动播放，必须在用户交互后才能播放。

  2. 静音视频允许自动播放 添加 muted 属性的视频可以自动播放，但移动端仍需 playsinline 属性配合。

  3. Web Audio 需用户交互启动 AudioContext 处于 suspended 状态，必须在用户手势中调用 resume() 才能启动。

  4. 后台标签页媒体播放节流 页面切到后台后，视频解码优先级降低，可能掉帧；音频播放不受影响。

用户激活（手势）要求

  1. 获取媒体设备需用户交互 navigator.mediaDevices.getUserMedia() 必须在用户点击等手势回调中调用。

  2. 剪贴板写入需用户交互 navigator.clipboard.writeText() 必须在用户手势中调用，读取权限更严格。

  3. 全屏请求需用户交互 element.requestFullscreen() 必须在用户手势中调用。

  4. 通知权限请求需用户交互 Notification.requestPermission() 必须在用户手势中调用，否则静默失败或自动拒绝。

  5. 弹出窗口需用户交互 window.open() 如果在非用户触发的上下文中调用（如页面加载、异步回调），会被浏览器拦截。

  6. 鼠标锁定需用户交互 element.requestPointerLock() 必须在用户手势中调用。

  7. 自动下载需用户交互 通过创建 <a> 或 iframe 触发的下载，必须在用户手势的同步回调中执行。

  8. 支付 API 需用户交互 PaymentRequest.show() 必须在用户手势中调用。

  9. 设备 API 需用户交互 Web Bluetooth、Web USB、Web Serial 等设备 API 都需要用户手势触发。

  10. 用户激活有有效期 一次用户交互产生的激活状态，只能用于同步或短时间内的异步操作（通常几秒内），超时后失效。

存储与权限

  1. 第三方 Cookie 默认禁用 跨站请求不携带 Cookie，影响单点登录和跨域身份验证。

  2. 存储配额限制 localStorage 通常限制 5-10MB，IndexedDB 有配额（通常数百 MB），超出会写入失败。

  3. 无痕/隐私模式存储临时性 隐私模式下，localStorage、IndexedDB、Cache API 等存储在关闭标签页后被清除。

  4. 存储持久化需申请 默认存储可能被浏览器自动清理，需通过 navigator.storage.persist() 请求持久化存储。

  5. 敏感 API 需要 HTTPS getUserMedia、Geolocation、Service Worker、Clipboard、Notifications 等必须在 HTTPS 或 localhost 下运行。

  6. Cookie 的 SameSite 默认限制 未设置 SameSite 的 Cookie 默认为 SameSite=Lax，跨站请求不发送。

  7. Cookie 的 Secure 要求 SameSite=None 的 Cookie 必须同时设置 Secure，即只能在 HTTPS 下传输。

页面生命周期

  1. 后台标签页定时器节流 setTimeout / setInterval 在后台标签页的最小延迟被钳制到 1000ms（部分浏览器更高）。

  2. 后台标签页 requestAnimationFrame 暂停 requestAnimationFrame 在后台标签页停止执行或大幅降低频率。

  3. bfcache 导致状态丢失 用户点击后退/前进时，页面从 bfcache（后退/前进缓存）恢复，不会重新执行初始化脚本。

  4. 页面可见性检测 需通过 Page Visibility API 检测页面是否可见，以决定是否执行动画、轮询等操作。

跨域安全

  1. CORS 限制 跨域请求需服务器返回正确的 Access-Control-Allow-Origin 等头，否则请求被拦截。

  2. 非简单请求需预检 PUT、DELETE 或带自定义头的请求，浏览器先发送 OPTIONS 预检请求，预检失败则实际请求不发送。

  3. 跨域资源加载受限 字体、Canvas 图片等跨域资源未设置 CORS 头时，Canvas 被“污染”，无法调用 toDataURL()、getImageData() 等方法。

  4. 跨域 iframe 访问限制 跨域的 iframe 无法通过 JavaScript 访问其内容（同源策略）。

  5. postMessage 需验证来源 跨窗口通信需验证 event.origin，防止恶意页面伪造消息。

弹窗与导航

  1. 非用户触发的弹窗拦截 window.open()、alert()、confirm() 等在非用户手势中调用会被拦截或静默失败。

  2. 一个手势仅允许一次弹窗 同一个用户手势回调中多次调用 window.open()，只有第一次生效。

资源加载

  1. 混合内容阻止 HTTPS 页面中加载 HTTP 资源（图片、脚本、音视频）会被阻止或降级，现代浏览器默认阻止主动混合内容（脚本、iframe）。

  2. 预加载资源限制 <link rel="preload"> 只能用于当前页面资源，且受 CORS 和 Content-Security-Policy 限制。

  3. 字体跨域限制 Web 字体跨域加载需 CORS 头，否则不生效。

内容安全策略（CSP）

  1. script-src 限制脚本来源 CSP 可通过 script-src 限制只允许特定域名的脚本执行，内联脚本需 nonce 或 unsafe-inline。

  2. style-src 限制样式来源 类似地，style-src 限制 CSS 来源，内联样式也受限。

  3. 禁止 eval 执行 CSP 默认或通过 unsafe-eval 控制是否允许 eval()、setTimeout(string) 等动态代码执行。

  4. 限制图片、字体、媒体来源 通过 img-src、font-src、media-src 等指令限制资源加载来源。

  5. 上报机制 CSP 可配置 report-uri 或 report-to，将违规行为上报到服务器。

权限 API

  1. 权限状态可查询但不可滥用 navigator.permissions.query() 可查询权限状态，但部分权限（如通知）查询可能受限制。

  2. 权限请求有频率限制 频繁请求同一权限（如地理位置）会被浏览器静默阻止或显示“不再询问”。

移动端特殊限制

  1. iOS 自动播放额外限制 iOS Safari 中，即使 muted 视频也需 playsinline 属性才能自动播放。

  2. iOS 禁止自动聚焦 移动端 Safari 不支持 autofocus 属性，且页面加载时调用 focus() 无效。

  3. 移动端触摸滚动时事件延迟 touchstart 中执行复杂逻辑会影响滚动性能，浏览器可能将事件标记为 passive 以提升滚动流畅度。

  4. 添加到主屏幕后的行为差异 PWA 或网页添加到主屏幕后，全屏模式下某些 API（如 window.open）行为与浏览器内不同。

其他限制

  1. WebAssembly 内存上限 WASM 线性内存有上限，通常 2GB 左右，超过则分配失败。

  2. SharedArrayBuffer 需跨域隔离 SharedArrayBuffer 需站点配置跨域隔离头（Cross-Origin-Opener-Policy 和 Cross-Origin-Embedder-Policy）才能启用。

  3. 大整数运算限制 BigInt 运算性能较普通 Number 差，且无法与 Number 混用。

  4. 性能 API 精度限制 为防范侧信道攻击，performance.now() 精度被限制（通常 100μs 或更低）。

  5. 定时器嵌套限制 setTimeout 嵌套超过 5 层后，最小延迟被钳制到 4ms。

  6. 同步 XMLHttpRequest 已废弃 主线程上使用同步 XMLHttpRequest 已被移除或报警告，推荐使用异步或 fetch。

2.2 日常遇到的策略

2.2.1 无法自动加载音视频

核心原因： 现代浏览器（Chrome, Safari, Edge, Firefox）为了提升用户体验和节省流量，实施了严格的自动播放策略。

  • 静音优先原则：默认只允许静音 (muted) 的音视频自动播放。
  • 用户交互原则：若要播放有声内容，必须先有用户的主动交互行为（如点击、触摸、按键）。
  • 媒体参与度指数 (MEI)：桌面端浏览器会根据用户在该站点的历史播放行为计算得分，得分高才可能允许有声自动播放，但此机制越来越严格且不可靠。

解决方案：

  1. 默认静音 + 取消静音策略（推荐）

    • 在 <video> 或 <audio> 标签中添加 muted 属性，确保能自动启动。
    • 在用户首次交互（如点击页面任意位置）后，通过 JS 移除 muted 属性或调用 play() 开启声音。
    <video id="myVideo" autoplay muted playsinline>
  <source src="video.mp4" type="video/mp4">
</video>
<script>
  document.addEventListener('click', () => {
    const video = document.getElementById('myVideo');
    video.muted = false; // 用户交互后开启声音
  }, { once: true });
</script>

    注意：移动端需添加 playsinline 属性以防止强制全屏。

  2. 拦截 play() Promise

    • 直接调用 play() 可能会抛出 NotAllowedError，必须进行捕获处理，避免控制台报错影响逻辑。
    const playPromise = video.play();
if (playPromise !== undefined) {
  playPromise.then(_ => {
    // 自动播放成功
  }).catch(error => {
    // 自动播放被阻止，显示播放按钮引导用户点击
    console.log("自动播放被阻止，需用户交互");
  });
}

  3. 微信/WebView 特殊处理

    • 在微信内置浏览器中，有时需要监听 WeixinJSBridgeReady 事件后才能执行播放操作。

2.2.2 页面交互未交互无法聚焦

核心原因： 浏览器安全策略规定，焦点管理（Focus） 必须由用户手势（User Gesture）触发。如果脚本在页面加载时或非用户触发的事件中强行调用 element.focus()，浏览器会忽略该请求，以防止恶意网站劫持键盘输入或弹出软键盘干扰用户。

解决方案：

  1. 绑定到真实用户事件

    • 确保 focus() 调用发生在 click, touchstart, keydown 等事件的回调堆栈中。
    // ✅ 正确：在点击事件中直接聚焦
button.addEventListener('click', () => {
  inputElement.focus();
});

// ❌ 错误：在异步操作或定时器中直接聚焦（此时用户手势上下文已丢失）
setTimeout(() => {
  inputElement.focus(); // 可能被忽略
}, 1000);

  2. 利用 requestAnimationFrame 争取时间片

    • 如果在复杂的异步流程后需要聚焦，尝试将 focus() 放入 requestAnimationFrame，但这并不总能绕过限制，取决于浏览器版本。
    someAsyncOperation().then(() => {
  requestAnimationFrame(() => {
    inputElement.focus();
  });
});

  3. UI 引导替代方案

    • 如果无法自动聚焦，设计明显的视觉提示（如高亮边框、动画跳动），引导用户手动点击输入框。这是最符合无障碍设计（Accessibility）的做法。

2.2.3 setInterval 最小化浏览器后不再执行

核心原因： 为了节省电量（移动端）和 CPU 资源（桌面端），现代浏览器（尤其是 Chromium 内核）对后台标签页（Background Tabs） 或 最小化窗口 实施了节流（Throttling） 策略。

  • 表现：当页面不可见时，setInterval 和 setTimeout 的执行频率会被强制降低，通常最低限制为 1000ms (1秒) 执行一次，甚至完全暂停（如 iOS Safari 在某些极端情况下）。
  • 影响：倒计时不准、心跳包丢失、动画卡顿。

解决方案：

  1. 使用 Web Worker（最佳方案）

    • Web Worker 运行在独立线程中，不受主页面渲染线程节流策略的影响，定时器在后台依然精准执行。
    // main.js
const worker = new Worker('timer-worker.js');
worker.onmessage = (e) => {
  console.log('收到心跳:', e.data);
  // 更新 UI 或发送数据
};

// timer-worker.js
setInterval(() => {
  postMessage({ time: Date.now() });
}, 500); // 即使在后台也能保持 500ms 频率

  2. 基于时间戳的修正算法

    • 不依赖计数次数，而是记录“开始时间”，每次执行时计算 当前时间 - 开始时间 来推导真实进度。这虽然不能解决“停止执行”的问题，但能解决“执行变慢导致数据不准”的问题。
    let startTime = Date.now();
setInterval(() => {
  let elapsed = Date.now() - startTime;
  // 根据 elapsed 计算真实的倒计时剩余时间，而不是 count--
  updateUI(elapsed);
}, 1000);

  3. 使用 visibilitychange 事件补偿

    • 监听页面可见性变化，当页面从后台切回前台时，立即执行一次补偿逻辑或重新校准时间。
    document.addEventListener('visibilitychange', () => {
  if (!document.hidden) {
    // 页面重新可见，立即校准或执行一次任务
    calibrateTimer();
  }
});

  4. Audio Hack (不推荐，已被修复)

    • 早期曾通过播放静音音频来欺骗浏览器认为页面处于活跃状态，但在新版浏览器中已基本失效且消耗资源，不建议使用。

2.2.4 CORS 跨域问题

核心原因： 浏览器的同源策略（Same-Origin Policy） 限制了不同源（协议、域名、端口任一不同）之间的资源访问。CORS 是一种机制，允许服务器通过响应头告诉浏览器哪些跨域请求是合法的。

解决方案：

  1. 后端配置 CORS 响应头（标准解法）

    • 在后端代码（Node.js, Java, Python, Go 等）中设置响应头。
    • 关键 Header：
      • Access-Control-Allow-Origin: 指定允许的源（生产环境严禁设为 * 如果涉及凭证）。
      • Access-Control-Allow-Methods: 允许的方法 (GET, POST, PUT...)。
      • Access-Control-Allow-Headers: 允许的自定义头 (Content-Type, Authorization...)。
      • Access-Control-Allow-Credentials: 是否允许携带 Cookie (设为 true 时，Origin 不能为 *)。
    • 预检请求 (OPTIONS)：后端必须正确处理 OPTIONS 请求，直接返回 200 及上述 Header。

  2. Nginx 反向代理（生产环境推荐）

    • 原理：前端请求同源的 Nginx，Nginx 转发给后端。浏览器认为请求是同源的，从而绕过 CORS 限制。同时可以在 Nginx 层统一添加 CORS 头。
    • 配置示例：
    server {
    listen 80;
    server_name api.example.com;

    location / {
        # 反向代理到实际后端
        proxy_pass http://backend_server_ip:port;

        # 动态获取请求源并回显，支持多域名且允许携带 Cookie
        if ($http_origin ~* "^https?://(www\.example\.com|admin\.example\.com)$") {
            add_header Access-Control-Allow-Origin $http_origin;
            add_header Access-Control-Allow-Credentials true;
        }

        # 处理预检请求
        if ($request_method = OPTIONS) {
            add_header Access-Control-Allow-Origin $http_origin;
            add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS";
            add_header Access-Control-Allow-Headers "Content-Type, Authorization";
            add_header Access-Control-Max-Age 1728000;
            add_header Content-Type text/plain charset=UTF-8;
            add_header Content-Length 0;
            return 204;
        }
    }
}

  3. 开发环境代理 (Dev Proxy)

    • 在使用 Vite, Webpack, Vue CLI, Create React App 等脚手架时，配置 proxy 选项。
    • 例如 vite.config.js:
    export default {
  server: {
    proxy: {
      '/api': {
        target: 'http://backend-api.com',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, '')
      }
    }
  }
}

  4. 其他方案（特定场景）

    • JSONP：仅支持 GET 请求，老旧技术，现代项目很少使用。
    • postMessage：适用于父子 iframe 之间或窗口间的通信，不属于 HTTP 请求跨域。
    • WebSocket：虽然 WS 协议本身不受同源限制，但握手阶段仍受 Origin 检查，需后端校验 Origin 头。

总结建议：

  • 开发阶段：使用构建工具的 Proxy。
  • 生产阶段：首选 Nginx 反向代理 或 后端完善 CORS 配置。不要试图在前端通过插件或黑科技绕过 CORS，那是浏览器的安全底线。
